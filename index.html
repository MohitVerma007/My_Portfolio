ZigMe

Backend Engineer · AI-powered recruitment

AI recruitment platform connecting companies with top talent through targeted job postings and automated candidate screening.

Candidate portal→Node.js API→Application service→PostgreSQL→Vector search→Recruiter dashboard

Business context

Companies face massive hiring overhead, unorganized candidate applications, and slow manual shortlisting: build an enterprise recruitment platform. I owned the backend architecture, multi-tenant database design, and AI-powered candidate screening.

Edge cases handled

  • Duplicate or concurrent applications for the same candidate and job
  • Access isolation across candidates, recruiters and college placement cells
  • Relevant candidate profiles without exact job-description keywords
  • Growing application volume affecting query and screening performance

Architecture and trade-offs

  • PostgreSQL for relational workflows. Candidates, jobs and applications benefit from constraints and transactions.
  • RBAC for multi-role access. Role-based permissions separate candidate, recruiter and placement-cell workflows.
  • Vector search over keyword-only matching. Semantic similarity surfaces relevant profiles even when wording differs.
  • AI-assisted screening, not automated hiring. Screening supports recruiter decisions rather than replacing human judgment.

EduPods

Full Stack & AI Engineer · AI-powered EdTech

An AI homeschooling platform with Ora, a personalized learning companion, curriculum-aligned lessons, collaborative learning pods and parent/facilitator progress dashboards.

Student experience→Backend APIs→AI orchestration→OpenAI API→Learning data→Progress dashboards

Business context

EdTech startup lacking engagement and tracking: build an AI-powered personalized learning platform. I owned the backend, AI companion integration, and server cost optimization.

Edge cases handled

  • AI responses drifting outside the lesson or curriculum context
  • OpenAI API timeouts, rate limits and temporary provider failures
  • Repeated questions increasing token usage and inference costs
  • Different learning needs requiring appropriate prompt and model behavior

Architecture and trade-offs

  • Centralized AI orchestration. Prompts, context and model selection are managed in one layer.
  • Model routing over one-size-fits-all usage. Simpler queries use smaller models while complex tasks use more capable models.
  • Caching for repeated questions. Frequently asked questions can be served without another LLM request.
  • Retry with exponential backoff and jitter. Transient provider failures are retried without creating retry bursts.

Hunger

Personal build · In development

A Zomato-like food delivery platform connecting customers, restaurants and delivery partners through ordering, payments, dispatch and live order tracking.

Customer app→REST API→Order service→PostgreSQL + Redis→Queue / workers→Restaurant + delivery partner

Business context

Two founders, a single app prototype for food delivery, and a deadline: a demo-ready product before the pre-seed pitch. I owned the core stack, real-time order state machine, and the pitch demo.

Edge cases being addressed

  • Duplicate order creation and payment retries from repeated requests
  • Payment gateway delays, failed webhooks and safe payment-state reconciliation
  • Restaurant acceptance, rejection and order-state transitions
  • Concurrent delivery-partner assignment and reliable order-status updates

Architecture and trade-offs

  • Modular monolith over early microservices. A Node.js + TypeScript codebase keeps development and deployment manageable while preserving clear module boundaries.
  • PostgreSQL as the source of truth. Orders, payments and state transitions need relational integrity and transactions.
  • Redis for caching and rate limiting. Frequently accessed data and traffic controls stay off the primary database path.
  • Queue, workers and outbox for background work. Notifications and asynchronous processing can run without blocking customer-facing APIs.
  • WebSockets for live updates. Order and delivery status can be pushed to clients as the lifecycle progresses.
